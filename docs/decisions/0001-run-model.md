# 0001. Модель запуску шаблону: копія в запуск, запис лише через функції, видимість за роллю

- Статус: прийнято
- Дата: 2026-10-20
- AC: AC-RUN-01, AC-RUN-02, AC-RUN-04, AC-RUN-05, AC-RUN-06, AC-RUN-08, AC-RUN-09, AC-TASK-06

## Контекст

Вимоги PM свідомо лишають відкритим, як зберігати шаблони, запуски й права доступу. Специфікація (`run-launch`, `run-tracking`) вимагає, щоб запуск зберігав шаблон таким, яким він був у момент запуску (AC-RUN-02), щоб кожна задача мала рівно одного виконавця (AC-RUN-04, AC-RUN-08, AC-RUN-09) і щоб менеджер бачив лише свої запуски або ті, де він виконавець (AC-TASK-06). supabase-js не має транзакцій: кілька записів разом потребують однієї функції Postgres. План — `openspec/changes/impl-run-tasks/design.md` (D2–D4).

## Рішення

- **Копія в запуск.** Шаблон (`templates`, `template_sections`, `template_tasks`) і запуск (`runs`, `run_sections`, `run_tasks`) — окремі таблиці. Запуск **копіює** секції й задачі шаблону (назва, `required`, порядок), тож подальші зміни шаблону запуск не зачіпають (AC-RUN-02). `run_tasks` створюється по одному на кожну задачу шаблону; `assignee_id` обов'язковий.
- **Запис лише через функції.** `authenticated` має тільки `select` на таблиці запусків. Запуск створює `public.launch_run` (`security invoker`), що викликає `private.launch_run` (`security definer`, `set search_path = ''`): у одній транзакції перевіряє назву, створює запуск і копії, призначає виконавців (за замовчуванням — менеджер запуску). `execute` відкликано в `public` і `anon`, видано `authenticated`.
- **Видимість.** `private.can_see_run(run_id)` (`security definer`): admin бачить усі запуски, manager — запуски, де він менеджер запуску або виконавець хоча б однієї задачі (AC-TASK-06). Політики `select` на `runs`, `run_sections`, `run_tasks` викликають цей хелпер, тож не посилаються одна на одну (42P17).
- **Вибір виконавця.** `list_assignable_users` повертає лише `id` і `email` користувачів manager/admin; RLS на `profiles` не послаблюємо (робоче припущення до питання PM solomchaak/property-workflows-spec#5).
- **Шаблони.** Читають усі автентифіковані користувачі; запис лише `service_role` або міграція (екран створення шаблонів поза цим зрізом).

## Розглянуті варіанти

- Запуск посилається на задачі шаблону й зберігає лише зміни — складніший запит і слабша гарантія незмінності (AC-RUN-02).
- Прямі `insert` у `runs` і `run_tasks` для `authenticated` з політиками — користувач міг би створити задачі в обхід `launch_run` (довільні назви, виконавці).
- Кілька запитів з server action — без транзакції запуск міг би лишитися без частини задач.
- Один `security definer`-виклик із `public` — заборонено правилами проєкту: definer лише в схемі `private`.

## Наслідки

- Правила запуску живуть у Postgres, тож їх перевіряє `db-check` (міграції) і тести бази; у CI `app` бази немає, тому AC із правилами лише в базі лишаються «відкладено (DB-тести не запускаються в CI)».
- Зміна відповіді PM (Q1–Q4) торкається окремих місць: вибір виконавця, текст для чужого запуску, обрізання назви, секції.
- Копіювання збільшує обсяг даних запусків, але робить їх незалежними від шаблонів.
